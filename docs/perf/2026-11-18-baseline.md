## 1. 结论摘要

1. **当前真实规模（≤1 万条记录、50 用户）没有任何性能问题**：所有被测端点 p95 ≤ 10ms，其中 6 个端点 p95 ≤ 2.5ms。**不需要加缓存**。
2. **两处「取最新一条」的 ORM 查询缺 `.limit(1)`，是本次唯一的数量级问题**：
   - `services/warning_service.py:22` 取最新 `HealthRecord`：每人 1 万条记录时 **107.01 ms**，加 `.limit(1)` 后 **5.61 ms（19×）**；
   - `services/mental_service.py:243` `_health_rating_danger` 取最新 `HealthAnalysis`：1 万条分析时 **85.90 ms**，加 `.limit(1)` 后 **0.95 ms（90×）**。
   两者都把整张用户历史一次性实例化成 ORM 对象，再丢掉 99.99%。`/api/warning/check` 在 5 万条数据下 130ms 耗时里，**SQL 执行只占 6.5ms，其余 95ms 全是这一步的对象构造**。
3. **`GET /api/health/records` 无分页**（`services/health_record_service.py:47` 返回该用户全部记录）：每人 1 万条时端点 **265 ms**，是全部端点里最慢的，且响应体随历史线性膨胀。
4. **health 三表（`health_records` / `health_warnings` / `health_analyses`）没有任何 user 维度索引**，全部 `SCAN + USE TEMP B-TREE FOR ORDER BY`。但在 1 万行量级下索引收益只有 ~1.2×（落在抖动内）；**50k 行/单用户 1 万行时「最新健康记录」单条 SQL 从 4.045 ms 降到 0.062 ms（65×）**。结论：**先修 `.limit(1)`，索引留到单表 > 10 万行再上**；顺序反了会在低行数下反而变慢（见 §5 的 1.3–2.0× 回退）。
5. **明确的 N+1 只有一处**：`warning_service._persist_warnings` 对每条预警单独 `SELECT` 去重（每类 2 条 SQL），最坏约 8 类 → 16 条。其余端点的「多 SQL」是固定条数的聚合查询（`/api/mental/summary` 6 条、`/api/warning/stats` 3 条），不是 N+1。

> 本文只给基线、定位与建议，**不改业务代码**（P-1 明确约束）。第 8 节按能力域标注归属。

## 2. 测量方法

### 2.1 脚本

```bash
# 标准基线（真实规模）
PYTHONUTF8=1 uv run python scripts/bench_health_queries.py --sizes 1000 10000 --users 50 --iterations 30 --rounds 2

# 单用户数据量放大（暴露全表扫描 / 无 LIMIT）
PYTHONUTF8=1 uv run python scripts/bench_health_queries.py --sizes 10000 50000 --users 5 --iterations 20 --rounds 2

# 索引假设对照（只在临时库建候选索引，不动仓库与真实库）
PYTHONUTF8=1 uv run python scripts/bench_health_queries.py --sizes 10000 --users 50 \
    --iterations 10 --rounds 1 --query-iterations 30 --simulate-index
```

- 每次运行创建**两个临时 SQLite 库**（`plain` / `indexed`），同一 seed，测完即删（`--keep-db` 可保留）。
- 端点通过 `httpx.ASGITransport` 直连 `main.app`，绕开网络与 uvicorn，保留路由、依赖注入、Pydantic 序列化与 SQLAlchemy 会话。
- 每端点每轮采样 `--iterations` 次，多轮（`--rounds`）取**每端点最好一轮**的 p50/p95（消除机器抖动，口径比单轮平均更接近「该代码的下界成本」）。
- 每请求 SQL 条数由 `before_cursor_execute` 事件计数器统计。
- `--query-iterations` 直接对 `QUERY_PLANS` 里的 7 条 SQL 计时，剥离 HTTP 与序列化开销，用于判断「扫描本身到底多贵」。
- 种子数据：`users` 个用户均分 `records` 条健康记录（身高体重血压等字段全量）+ 每人 30 天心理打卡 + 每人 `min(max(5, 记录数//2), 200)` 条预警（随机 `is_read`）+ 每 10 人一条危机量表 + 每人 1 条 `HealthAnalysis`。
- 被测端点：`GET /api/warning/list`、`GET /api/warning/list?is_read=false`、`POST /api/warning/check`、`GET /api/warning/stats`、`GET /api/health/records`、`GET /api/health/rating/latest`、`GET /api/mental/trend?days=30`、`GET /api/mental/summary`。

### 2.2 口径说明

- 绝对毫秒数受机器状态影响（实测同一配置两轮可差 ±20%），**结论只看量级与同机同轮内的相对差**。
- 端点级 p50 差异 < 0.5ms 一律视为持平；因此索引对照结论主要采信 §5 的**单条 SQL 级**数据。

## 6. 决定性微基准（缺 `.limit(1)`）

| 场景 | 现实现 | 加 `.limit(1)` | 倍数 |
|---|---|---|---|
| `warning_service` 取最新 `HealthRecord`（每人 10 000 条记录） | **107.01 ms** | **5.61 ms** | **19.1×** |
| `health_record_service.get_records` 全量列表（每人 10 000 条） | **88.40 ms** | —（需分页） | — |
| `warning_service.check_health_warnings` 整体 | 105.38 ms | — | — |
| `mental_service._health_rating_danger` 最新 `HealthAnalysis`（10 000 条分析） | **85.90 ms** | **0.95 ms** | **90.4×** |
| `mental_service.is_serious_mode` 整体 | 90.48 ms | — | — |
| `safety_service.assess_user_risk`（已用 `.limit(1)`） | 5.58 ms | — | — |

逐语句追踪 `/api/warning/check`（5 万条 / 5 用户，总 101.5 ms）：

```
  6.02 ms  SELECT health_records ...            ← 唯一的大头，且只为了取 1 行
  0.15 ms  SELECT mental_records.sleep_hours ...
  0.04 ms  SELECT health_analyses ...
  0.03 ms  SELECT scale_assessments ...
  0.04 ms  SELECT mental_records.record_date ...
  0.12 ms  SELECT health_warnings ...（去重 bmi）
  0.05 ms  SELECT health_warnings ...（去重血压）
  0.05 ms  SELECT health_warnings ...（去重心率）
  0.05 ms  SELECT health_warnings ...（去重体温）
```

SQL 执行累计 ≈ 6.5 ms，请求 101.5 ms → **约 95 ms 花在把 1 万行实例化成 ORM 对象再取第一行**。这正是 6.02 ms 与 107 ms 的差距来源（`before/after_cursor_execute` 不计结果集构造）。

## 7. 结论

| 项 | 结论 |
|---|---|
| 是否需要缓存（Redis / 进程内） | **不需要**。p95 ≤ 10ms 的端点上叠加缓存只会引入一致性风险 |
| 是否需要索引 | **当前不需要**；单表 > 10 万行再评估，且必须与 §8-① 一起做 |
| 真正的瓶颈 | ① 两处缺 `.limit(1)` 的全量实例化；② `/api/health/records` 无分页；③ `_persist_warnings` N+1 |
| 固定条数聚合 | `stats` 3 条 count 子查询、`summary` 6 条（3 条同表）可合并，收益 <3ms，优先级最低 |

## 8. 建议（按性价比，标注归属域）

| 优先级 | 建议 | 预期收益 | 归属 |
|---|---|---|---|
| ① | `services/warning_service.py:22` 与 `services/mental_service.py:243`、`mental_service.py:279` 的「取最新一条」查询加 `.limit(1)` | 19× / 90×（1 万行时 107ms→5.6ms、86ms→0.95ms），改动 1 行/处，无行为变化 | 数据/数据库 = opencode（`warning_service.py` 已被 K-1 认领为 kilo，需按文件所有权确认） |
| ② | `GET /api/health/records` 增加 `limit`/`offset`（或 `days`）并与前端契约对齐 | 1 万行时 265ms → <10ms，且响应体不再线性膨胀 | 接口/兼容性 = kilo（契约变更）+ 前端 = Claude |
| ③ | `_persist_warnings` 改为「一次 `SELECT ... WHERE warning_type IN (...)` + 批量插入」 | 9–16 条 SQL → 2–3 条，check 端点再降 ~3ms（低行数下主要是抖动级） | K-1 认领方（kilo） |
| ④ | 单表 > 10 万行时再加 3 个候选索引（`ix_health_records_user_date` / `ix_health_warnings_user_created` / `ix_health_analyses_user_date`） | 50k 行时最新记录 4.0ms→0.06ms；10k 行时**负收益** | opencode（模型/迁移）+ 本条须在 ① 之后再做 |
| ⑤ | `warning/stats` 3 条子查询合并、`mental/summary` 3 条量表查询合并 | <3ms，纯整洁性 | 收益太低，可不动 |

**复测触发条件**：K-1（健康数据变更自动触发预警）与 K-2（`/api/health/rating/history`）合并入 `main` 后，重跑本脚本同口径，与本文数字对比；若 ①③ 已落地，本文件应被更新而不是新增文件。

## 9. 复现注意

- 必须带 `PYTHONUTF8=1`（Git Bash 下默认 cp936，中文输出会乱码）。

- `--json out.json` 可留存完整结果（含 EXPLAIN 计划与逐端点样本），本文表格即由该 JSON 整理。
